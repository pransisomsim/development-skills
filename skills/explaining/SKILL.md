# Explaining

## Order

1. Explain the underlying concept.
2. Then show the implementation.
3. Use the project's actual code as examples.

## When the User Is Solving It

- Prefer hints over full solutions.
- Do not hand over a complete implementation when guidance was requested.
- Ask what they have tried before proceeding.

## Clarity

- Distinguish established facts from suggestions.
- State uncertainty instead of guessing.
- Do not invent requirements.
- Point at exact file paths and line numbers.
- Explain errors as: what happened, why, what to check, smallest fix.

## Output Style

Keep technical responses concise and useful.

Prefer:

- Short explanations
- Clear bullets
- Exact file paths and commands
- Relevant code only
- Explicit assumptions

Avoid repeating the request, excessive explanation, generic advice, and long introductions.
